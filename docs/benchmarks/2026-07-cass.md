# rogrep vs cass — benchmark (2026-07-29)

Comparison against [cass](https://github.com/Dicklesworthstone/coding_agent_session_search)
(coding_agent_session_search), the closest tool in spirit: a local indexer/
searcher over coding-agent session history. cass stores sessions in SQLite
and serves lexical search from SQLite FTS5 (via its frankensqlite fork);
semantic search is opt-in (a separate ~90MB model download) and was **not**
enabled, so this measures the out-of-the-box configuration of both tools:
lexical search — tantivy (rogrep) vs SQLite FTS5 (cass).

Reproduce with [`scripts/bench-vs-cass.sh`](../../scripts/bench-vs-cass.sh);
both tools index into throwaway data dirs (real indexes untouched) and read
the same on-disk sessions.

## Environment

- Intel Xeon E-2286M (16 threads, 2.4GHz), 31GiB RAM, Samsung 970 EVO Plus
  NVMe, Linux 6.8
- rogrep 0.1.0 (`7a1a249`), release build, Rust stable 1.95
- cass 0.6.22 (`aaff7dc`), release build from source with its pinned
  nightly toolchain
- Corpus: this machine's real session history — ~730MiB across ~275
  sessions (Claude Code, Codex, Cursor, Grok, plus the Hermes and opencode
  SQLite stores; the largest single session is a 73MB / 6,939-turn Codex
  rollout). Timings are single runs for the cold index and min/median/max
  over repeated runs elsewhere.

## Results

### Indexing

| Metric | rogrep | cass | ratio |
|---|---:|---:|---:|
| Cold full index (fresh data dir) | **20.9 s** | 416.4 s (6m56s) | **19.9×** |
| Warm no-op refresh, median of 5 | **16 ms** | 3,728 ms | **~230×** |
| Warm refresh min–max | 15–448 ms¹ | 2,796–6,336 ms | |

¹ the 448 ms outlier is a real incremental ingest: the benchmark itself ran
inside a live Claude Code session, so one refresh tailed that session's new
turns.

### Index footprint

| | rogrep | cass |
|---|---:|---:|
| Total data dir | **273 MB** | 2.2 GB |
| — full-text index | 208 MB (tantivy, turn text stored for excerpts) | 171 MB (FTS5) |
| — SQLite | 49 MB (metadata/stats only) | 833 MB (full message store) |

The architectures differ: cass copies all message content into SQLite (its
source of truth) and builds FTS5 on top; rogrep keeps source JSONL files as
the only durable truth and stores text once, in the search index. Both
re-derive from sources, but rogrep pays ~0.37× the corpus size on disk vs
~3× for cass on this corpus.

### End-to-end search latency

Wall time of one full CLI invocation (process start → exit), `--limit 10`,
min/median/max over 10 runs. rogrep's numbers *include* its automatic
staleness sweep on every command; cass does not re-index on query.

| Query | rogrep (ms) | cass (ms) | median speedup |
|---|---:|---:|---:|
| `tantivy` | 26 / **26** / 71 | 32 / 33 / 54 | 1.3× |
| `flaky test` | 23 / **24** / 34 | 99 / 101 / 112 | 4.2× |
| `swap OOM killer` | 21 / **21** / 38 | 69 / 71 / 85 | 3.4× |
| `gh pr create` | 35 / **36** / 91 | 87 / 89 / 107 | 2.5× |
| `conversation index rebuild` | 30 / **31** / 76 | 35 / 36 / 55 | 1.2× |
| `"cargo build --release"` (phrase) | 22 / **22** / 34 | 33 / 33 / 38 | 1.5× |

Both tools returned non-empty result sets for every query. Multi-term
queries show the largest gap — tantivy's positional index intersects terms
in microseconds, so rogrep's floor is process startup + the staleness
sweep, while FTS5 term intersection grows with posting-list size.

## Notes on fairness

- Both binaries are `--release` builds compiled on the same machine; each
  used its own pinned toolchain and its own default configuration.
- End-to-end CLI wall time is what a user or agent experiences, but it
  hides engine latency behind process startup (~10–15 ms for either
  binary). Engine-level query latency differences are larger than the
  end-to-end ratios suggest.
- The tools do not index byte-identical corpora: discovery rules differ
  (e.g. rogrep indexes only `chat_history.jsonl` for Grok and materializes
  Hermes/opencode from their SQLite stores; cass has its own connector
  set, and its cold ingest includes work rogrep doesn't do, like building
  analytics rollups). The corpus is the same on-disk session history
  either way.
- Ranking/result *quality* is not measured here — only latency, index
  cost, and footprint. cass's opt-in semantic mode (not enabled) serves a
  use case rogrep intentionally does not.
- Single-machine, single-day snapshot; both projects are moving targets
  (cass 0.6.22, rogrep 0.1.0).
